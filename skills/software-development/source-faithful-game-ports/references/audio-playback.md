# Audio playback qualification

Separate WAV/decoder tests, game sound requests, device-stream integration and subjective sound/latency quality. Proving one does not establish the others.

1. Inspect the resolved build features and native backend before changing code. Macroquad's real audio is an explicit feature; inspect Cargo's resolved target-specific features and the binary's actual linked libraries. If the installed registry package lacks `.cargo-checksum.json`, hash its cached `.crate` against the exact Cargo.lock checksum and compare the selected source bytes against the archive members before calling that source lock-bound. Missing extraction metadata is not permission to reinstall, modify the registry or assume provenance. Use `cargo metadata --offline --filter-platform x86_64-unknown-linux-gnu --format-version 1` for that Linux target: unfiltered metadata can request irrelevant Android dependencies absent from the offline cache. Do not enable downloads or change feature pins based only on an unrelated-platform cache miss.
For CPU-only decoder/control qualification, compile the exact lock-bound decoder/mixer source with a clearly identified data-only context adapter and the real application admission/bank/scheduler. Mirror the dependency's actual target-specific feature declaration (for quad-snd's native audrey path, disable defaults and retain `wav` plus `ogg_vorbis`); a standalone dependency's defaults can request unrelated uncached codecs. Read complete callee signatures before constructing the fixture, use a separate Cargo target, and compare its resolved dependency versions/checksums with the application. Check decoded length/capacity against the estimator, original-media coverage, independent handle identities and ordered stop behavior with discriminating negative controls. An intentionally caught malformed-decoder panic may appear on stderr: require the actual terminal exit and structured completion assertions rather than accepting or rejecting on that line alone. Label this literal decoder/control-path proof, never actual platform AudioContext, disposal acknowledgement, device flow or audible quality.

2. Reuse the maintained private graphical runner and ordinary-input recording. Omit its mute flag. Preserve isolated HOME/XDG/display state; when testing the existing real PipeWire device, pass the observed real runtime directory through child-only `PIPEWIRE_RUNTIME_DIR`. Do not change a server, default sink, volume, routing, services or persistent config to make the test pass. Audio playback can be audible: keep it bounded and distinguish it from a silent test.
3. Bind observations to the actual game child PID, executable, parent and start generation. Check loader results, runtime event counts, stderr/thread panics and reported underruns. Successful loading or `audio_events > 0` is not playback proof.
4. Query metadata only. `pactl --format=json list sink-inputs` can omit native ALSA/PipeWire clients. If so, parse `pw-dump` without emitting the whole graph. For each `Stream/Output/Audio` node, resolve `client.id`; inspect the client's `application.process.id` or `pipewire.sec.pid`, not only node properties. Credit only the owned game's PID. Retain only its sanitized node/client/link and selected sink fields; never record other applications' audio or dump unrelated command lines.
5. Require the owned node to be `running`, stereo links to be `active` with matching output/input node IDs, and the selected real default sink to be running and explicitly unmuted. Inspect the sink's mute state through `pactl --format=json list sinks`. Record the default sink before/after without changing it. A stream bound to another process, wrong device, suspended node, inactive/crosswired link or muted sink must not pass.
6. Add positive/negative identity controls to the observer. A failing observer can be a measurement bug rather than a game defect: preserve the failed attempt, demonstrate the missing native-client path, correct that path once, and rerun live into fresh create-only evidence. Never rewrite old failures or manufacture observations.
7. Record source/input/binary bindings, command exits, actual run metrics, native observation counts, owned-process cleanup and display preservation. A game can emit complete metrics and a valid final frame before process reaping fails: preserve those as partial gameplay evidence, keep the overall native check failed, and inspect the exact owned generation and its threads rather than assuming a zombie leader means completion. Confirm ownership release or prior-boot termination before a fresh probe; do not manufacture a receipt or merely extend the deadline. State limitations: active device flow is playback integration, not a recording, proof of audible quality, zero physical dropouts or latency acceptance. Software OpenGL accompanying the audio test remains non-hardware GPU evidence.
