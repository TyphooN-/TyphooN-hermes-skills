# Source-Bound Code and Evidence Review

## Portable scope

This copy preserves a locally developed workflow, not transferable approval. Resolve the current task, repository, active Hermes profile, tools and ownership on this machine first. Historical project choices and TyphooN-specific executor/build policies are context, not permission to start services, run targets, modify security settings or publish. Project-root variables are documented in the collection's `PORTABILITY.md`; unset variables are not usable paths. Installing a skill installs no external tools or plugins.

Review repository changes or frozen analysis/evidence packets through static scans,
baseline-aware proof and independent acceptance. Use a separately owned correction
loop when fixes are authorized; a review request alone does not authorize source
edits, runtime activation, commits or publication.

**Core principle:** Keep implementer self-review separate from independent acceptance. Fresh context finds what the implementer can miss.

## Operator safety and evidence contract

- Review the complete assigned tracked, unstaged and untracked source set. An empty staging index is not an empty implementation; do not stage files merely to make a reviewer see them.
- Preserve a dirty primary checkout. Build baseline comparisons in separate pinned disposable checkouts with the same test isolation and interpreter; never stash, reset, restore or switch the user's work to obtain a baseline.
- Use the project's canonical test runner and real guards. Matching guard-aborted failures do not establish behavioral compatibility. Preserve exact commands, exits, failure identifiers and source/environment bindings; parse counts programmatically.
- Inspect each saved check's actual receipt schema before auditing it: first branch on the top-level type (`dict` versus `list`), then print only bounded mapping keys or element types and one representative binding. Call `.keys()` or `.items()` only after establishing a mapping; inspect list elements before iterating their fields. Validate required keys before deriving counts, because an absent collection means unknown or schema mismatch, not zero. Once the shape is known, emit a compact audit row per check with its receipt reference, command/exit, binding mismatches and unique-case counts; keep full testcase inventories and logs private, reading only the portion needed to resolve a concrete failure or binding question. Printing whole receipts merely to inspect their schema can replay embedded logs into the supervisor's context. Rust libtest can emit `ignored, <reason>`: a recorder matching only bare `ignored` can preserve correct totals while omitting ignored identities. Reconcile those names from the original hashed log and qualify the parent projection; do not rewrite old receipts or rerun successful tests for that reporting mismatch. Check per-line truncation flags even for a small one-line JSON file, because a bounded text preview may omit required fields. Then compare exact argv/cwd/exit and every declared artifact/hash; a structured log may itself be the receipt. If source/log bindings validate but a parent audit fails on an assumed field or guessed diagnostic literal, inspect the relevant original receipt/log for the actual schema, failed testcase identity and exception/assertion text, then repair only the projection. Preserve the completed checks and original diagnostics; an observer-only mismatch is not reason to rerun product proof or inference. Locate each required completion claim in its actual saved envelope; never default an absent field to success. Preserve adapter failures separately from source failures, and publish final acceptance or completion status only after all required bindings validate.
- Derive saved-source capture scope from the actual recorder before auditing snapshot directories. A receipt can bind the full tree while saving only baseline-relative changed files; reconstruct the frozen baseline plus saved delta and verify the complete fingerprint instead of declaring selective capture missing/corrupt or rewriting the receipt.
- Keep evidence-file hashes, source-tree fingerprints and per-component input fingerprints in separately named fields. Compute an artifact reference's SHA256 from that file's original bytes, never substitute a source or component fingerprint. Trace each fingerprint's field projection, ordering and serialization before comparing it: candidate rows including modes and runner rows containing only path/size/hash can describe the same source with different digests. Validate each original fingerprint by its own producer's method, then reconcile complete per-path rows and separately required modes; never rewrite original identities to make unequal methods match. A bundle file digest can also differ from its component input digests, because valid digest syntax does not establish which object was hashed.
- Compact JSON only in separately identified review copies, preserving the original-byte hash, review-copy hash and verified value-equivalence mapping. Preserve types, array order, identifier case and command-string contents; a smaller serialization is not authority to normalize evidence. Keep receipt references bound to the original bytes, and label command evidence parent-reused unless independently executed.
- Match archive metadata tokens such as `.INSTALL` against preserved literal path components: `lstrip('./')` removes the leading dot and can fabricate absence. Use only the producer's explicitly qualified normalization, retain original member names, and distinguish an observer-only comparison repair from a subject failure.
- Reconcile ancillary execution labels against the original literal command or parsed exact shell body, effective cwd, exit and CLI-emitted output before accepting a command link. A reviewer prose item-ID typo does not invalidate an otherwise fully bound source judgment: preserve the report and append the exact mapping with its limitation. Never rewrite identifiers or shift commands to manufacture a match; unresolved command/cwd/exit provenance remains HOLD.
- Bind integrity-gated Python helper execution to the exact verified source bytes. `-B` and `sys.dont_write_bytecode` suppress bytecode writes, not reads; a cache-aware `SourceFileLoader` can select a pre-existing `.pyc` even when the source-file digest matches. For an already-authorized trusted source-only helper, require bounded source reading, digest verification and compilation of those same bytes without a cache-reading loader. Use guarded, explicitly constructed effect-free synthetic cache fixtures for regressions; this grants no authority to execute recovered/untrusted code or native cases.
- Derive execution-report flags from the actual operation boundary. Loading a helper, attempting its entrypoint, creating a child and observing child closure are distinct events; a failure in an earlier stage must not report a later event as having happened.
- Preserve command logs as bytes before rendering them into an inline review packet. Locale-dependent output, including GPG stderr public UIDs, can be non-UTF8 without being damaged. Verify the frozen raw-byte hash first; when UTF8 framing is required, use an explicitly labelled lossless encoding with the original digest and a checked decode round trip. Never use replacement decoding or silently normalize those bytes.
- Budget the fully rendered review packet before materializing or dispatching it: include line-number prefixes, semantic diffs, repeated source bodies, receipt JSON, schema and response headroom. Source-file byte totals omit that framing and duplication, so they can pass a size check while the actual packet exceeds it. Reduce only nonessential dependency scope or use the qualified restricted-reader route; never trim required changed code to force a fit.
- Deduplicate byte-identical review bodies only with an explicit alias map retaining every original path, relevant mode and role. Compute original-path coverage separately from unique content and executed-test counts. Mark JSON-pointer or instruction-window projections as partial coverage, never as inspection of the omitted source. Use the [compact-input qualification recipe](references/evidence-recovery.md#8-compact-review-inputs-without-changing-evidence-or-coverage) before freezing the packet.
- For this operator, use a separate Opus-Max Claude read-only lane for high-risk independent acceptance when available and permitted, following the claude-code skill and SOUL contract. Honor the latest project-specific executor exclusion; obtain explicit agreement for a different required review route, then use that approved route without waiting for the excluded provider. No recursive workers or inherited cloud route assumptions. A quota-failed or interrupted reviewer may leave useful evidence, but a missing terminal verdict is not acceptance.
- A completed reviewer response with a malformed or mismatched source identifier is not source-bound acceptance, even when its verdict says PASS/ACCEPT and its manifest digest matches. Preserve the exact rejected identifier and failed wrapper exit; never normalize or parent-edit it. After confirming process completion and unchanged inputs, permit one bounded full-verdict correction using the retained original source/user/assistant history verbatim, then validate the newly emitted identity and verdict separately.
- Distinguish a malformed ancillary report digest from the required primary source/manifest identity echoes. Reject the literal before lookup, preserve it unchanged, and never pad, normalize or repair it. An independent final verdict may explicitly classify an unused ancillary field as nonblocking when separately retained canonical manifests and actual file checks bind that artifact; document that exclusion without weakening primary-identity validation or rewriting the report.
- Keep frozen review sources and their manifests immutable. Verify the manifest file's own digest against the retained reviewer verdict or acceptance record before trusting its per-file hashes; rewriting both a source and its manifest can make an altered snapshot appear internally consistent. Never refresh those hashes to admit new code under an old PASS. Preserve any altered evidence, append an integrity notice, freeze the current candidate separately, and require fresh independent acceptance for changed or unprovable scope before integration or activation. Follow [altered-snapshot recovery](references/evidence-recovery.md#7-recover-an-altered-frozen-review-set). Give material findings to a separately owned executor; the independent reviewer must not fix its own findings.
- Publish supporting scope/check/preservation artifacts before a terminal verdict that references them, or embed them directly in one self-contained JSON result. Quota can interrupt finalization after a verdict file is written; missing named artifacts are still missing proof, even when reproduced BLOCK findings remain actionable.
- For restart-prone model-review runners, fsync a small public final-response/completion envelope before terminal-body assumptions, SDK cleanup or post-request provider/model/effort/tool/fallback guards, and before serializing bulky conversation history or rehashing a large source set. For Codex SSE, use the maintained native assembler: a completed frame can omit `response.output` while `output_item.done` carries the complete answer. Persist public answer items and the observed completion event early, excluding analysis/commentary/private reasoning; test null, empty, non-list and absent terminal output with forbidden-tool and incomplete-stream controls. Preserve the raw terminal's reported model separately: an assembler's `model` may be the configured request, not a served identity. Preserve public judgment separately from private reasoning. Before calling a successor a resumed review, verify that the runtime actually restored retained public conversation or source-bound inspection checkpoints; reusing a session ID alone proves neither restored context nor completed reading. If no history or verdict survives and another attempt is authorized, label it a reconstructed source-packet retry and credit no prior judgment. These checkpoints aid recovery but do not replace terminal completion, exact source identity, full scope or remaining required acceptance proof.
- Recover a review's requirements from its accepted task and current implementation contract before reusing interrupted scaffolding. Check literal CLI names and report schemas against those sources; an abandoned generator prompt is not authority to invent fields or redefine the objective. Preserve incorrect preparation separately and freeze a corrected source-bound packet without changing the implementation or rewriting its proof.
- Preflight the actual runner before constructing or invoking the reviewer: validate required state/schema/source bindings and create the required parent directories inside the new evidence root. Defer create-only per-run output leaves and receipts until managed-runtime imports and any bootstrap re-execution have finished; otherwise legitimate re-entry can collide with the first process's output directory. When adapting a retained runner to a different review schema, update its required packet keys, schema constants, final-response assertions and completion-field projections together before preflight; stale field names can reject a valid new judgment after inference. Before inference, cross-check every primary schema constant against the actual packet identities and require its path enum to represent the complete current inventory; exercise stale-hash, omitted-path and admission-flag negative controls through the real guard. A conflicting schema is a parent packet defect, not evidence that the reviewer miscomputed a hash; preserve the failed response, correct the schema and permit one complete bound-verdict correction rather than making a primary hash check log-only. Exercise reporting dependencies in that runner's actual bootstrap/tool-import context with the new packet, not only with a separate bare-interpreter import; runtime initialization can change module visibility. Preserve a pre-generation scaffolding failure as configuration evidence and correct only that preparation in a fresh output root with unchanged source bindings; it is neither a model-generation attempt nor a review verdict. If a complete model judgment instead survives a finalizer dependency failure, validate its original response through the qualified parent validator and preserve the worker's real failed exit; do not rerun the model just to regenerate packaging or alter shared dependencies to repair a private report.
- Treat the preferred 8 KiB terminal-verdict size as a presentation target, not an acceptance gate. Persist the original terminal response before optional formatting or size checks; oversize alone must not reject or hide a complete schema-valid, source-bound judgment. Retain large inventories, node lists, logs and receipt audits in separately hash-bound supports, then publish a small parent index after verifying those bindings. Before reading a large result, inspect its size or take a bounded first window; reduce it with code to the verdict, findings, source identity and declared supports instead of flooding supervisor context. Verify every declared support path/hash/mode, not guessed filenames.
- Inspect the frozen artifact catalog before updating controller status: an executor may have hash-bound lane.json or other apparently mutable metadata. Preserve every catalog-bound preimage and append a new parent completion/acceptance artifact instead of changing the original or weakening the catalog.
- Reconcile unexpected nonowned dirty-content drift against a separate owner's exact before/after content bindings before attributing it to the review lane. Preserve legitimate concurrent work and the original HOLD receipt; append a reconciliation artifact instead of restoring the file or claiming the entire primary checkout was unchanged.
- Commit or push only under the active request's authorization. Stage explicit owned paths, never `git add -A`, and never list Claude as a commit coauthor. The generic snippets below are examples, not permission to modify staging, clean a dirty checkout, bypass approvals or publish.
- Use search_files/read_file for static scans and targeted logs, and installed-tool help for actual delegation schemas. Do not copy outdated example parameters such as `goal=` or `toolsets=` into native delegate_task calls.

## When to Use

- After implementing a feature or bug fix, before `git commit` or `git push`
- When user says "commit", "push", "ship", "done", "verify", or "review before merge"
- After completing a task with 2+ file edits in a git repo
- After each task in subagent-driven-development (the two-stage review)
- When assessing whether to take an upstream or source-pin update, without implicitly authorizing implementation or activation

**Use a lighter path for:** low-risk documentation or configuration changes. Classify risk by behavior and blast radius, not extension; authentication, permissions, serving policy or security-boundary configuration still needs its required review and proof. An explicit scope reduction does not turn omitted verification into a pass.

**This skill vs github:** This skill reviews local source changes, upgrade candidates and verification evidence. `github` handles GitHub PR interactions such as inline comments.

## Step 1 — Get the diff

Classify the input before using Git. For a repository, inspect changes against the assigned pinned base, not an assumed `HEAD~1`; combine tracked staged/unstaged paths with nonignored untracked additions and keep the index unchanged. For preserved non-Git media or evidence, record HEAD/status as not applicable and review a named path/size/hash manifest, helper sources, derived reports and receipt bindings instead. Skip Git-only operations, not the review, and never initialize a repository merely to satisfy the harness. Read every assigned new source file explicitly.

Validate a generated patch with `git -C "$BASELINE" apply --check "$PATCH"` against the preserved preimage, not the already-patched candidate. A context or existing-file refusal on the postimage alone cannot classify the patch or implementation; preserve that diagnostic and check the named baseline without modifying either tree.

Resolve each reference through its producer-declared coordinate base before joining paths: artifact references, candidate manifests and a command's saved-source rows can use different roots in the same receipt. Do not recursively treat every `{path, bytes, sha256}` mapping as an evidence-root artifact, because embedded source rows can be relative to the command's snapshot. Dispatch inventory validation by object kind; validate symlink identities with `lstat`/`readlink` instead of dereferencing them or requiring regular-file-only fields. Verify portable source and intentionally transformed installed packages against their own manifests and producer bindings; a guessed root or an intentionally omitted development test is not evidence of corruption. Use the [typed receipt-audit procedure](references/evidence-recovery.md#2-validate-the-verifier-before-sweeping-evidence) before a full sweep.

For source/build-pin refreshes, validate preparations, acceptance records and every repeated immutable-input catalog as one metadata chain before freezing. Compare declared paths, byte lengths, modes and digests with the pinned producer and actual files, including explanatory or currently unconsumed catalog sections: their enclosing manifest can still be bound by review or admission. Regenerate stale derived rows from the canonical preparation rather than copying retired literals. Use the [derived custody-catalog correction procedure](references/evidence-recovery.md#refresh-a-derived-custody-catalog) to preserve valid correctness judgments while repairing a metadata-only spec HOLD.

Record the preservation baseline before review: capture HEAD, raw `git status --porcelain=v1 -z`, relevant index identities and the bytes, modes and hashes of dirty regular files. Parse NUL-delimited status records, including rename/copy records, and deduplicate the path union in code; staged and unstaged columns can refer to the same path. Keep submodule pointer and inner-worktree state distinct. Report unchanged content only for objects with matching retained content bindings: matching filenames, an unchanged status projection or one inventory digest cannot establish that the whole dirty checkout is unchanged. Preserve an older checkpoint's coverage gap explicitly instead of inventing its missing preimage.

If the diff exceeds 15,000 characters, review per file with bounded `read_file`/`search_files` lookups and `git diff <base> -- <owned-path>`. Confirm the complete path set against the manifest before acceptance.

Check the complete owned tracked and untracked delta for whitespace without staging it, before the final manifest refresh, full verification matrix and review freeze. Even an EOF-only repair changes hash-bound inputs and can invalidate otherwise fresh proof. Calibrate no-index difference versus whitespace-error exits with clean/bad controls and preserve diagnostics; use the concrete recipe in [verifier validation](references/evidence-recovery.md#2-validate-the-verifier-before-sweeping-evidence).

### Advisory branch — assess an upstream or source-pin update

For a request to check whether an update is worthwhile, complete this bounded assessment rather than automatically entering implementation, activation or commit phases. A recommendation is not independent acceptance of the candidate.

1. **Resolve three revisions once:** the installed runtime pin, any already-running candidate's frozen base, and the user's selected checkout HEAD/tree. Record package versions separately; an unchanged version string can hide substantial source changes. Preserve the dirty overlay or explicitly exclude it from the assessed scope. Do not fetch or chase a moving tip merely to answer a question about the selected source.
2. **Compare both relevant deltas.** Use `git diff --name-status "$INSTALLED_REV" "$SELECTED_REV"` for the overall upgrade and `git diff --stat "$CANDIDATE_REV" "$SELECTED_REV"` for changes beyond an existing candidate, then inspect the important files and interacting consumers. Preserve useful in-flight work at its recorded revision without duplicating its writer; its dependency/toolchain proof may be reusable, but its older source verdict cannot qualify newer bytes. Keep large diffs and inventories in artifacts, not model context.
3. **Trace benefits and migration risks before recommending a switch.** Check changed defaults, omitted response fields, input/output schemas and the callers that consume them, not just release notes. Treat a corrective or revert commit as a lead; its message is not evidence that current CI or client compatibility passes. Keep an upgrade assessment narrower than a whole-repository security audit and name the unassessed surfaces.
4. **Exercise the smallest permitted canonical proof.** Read repository instructions and package scripts, select relevant source-only tests when supported, and run them in a separate disposable copy rather than the frozen review inputs or live checkout. Record the exact selected paths, interpreter, argv, cwd, exit and logs; parse case/file totals in code and reconcile them with the selected scope. Verify that the tested source still matches the selected snapshot. Label source-only results separately from compiled adapters, transport tests and real-provider behavior.
5. **Answer the decision first:** recommend keeping the installed version, staging the selected revision, or waiting for an evidenced fix. Follow with the exact revision, practical benefits, compatibility caveats, executed proof and gates still needed before activation. Do not let a missing future activation verdict prevent a bounded advisory answer, and do not present that answer as the missing independent acceptance. Leave live pins and settings unchanged unless application is separately authorized.

## Step 2 — Static security scan

1. For refactors that extract methods into new modules, verify every cross-module symbol reference resolves to a real `def`/`class`/import in the target module before treating the extraction as structurally complete. A grep count of zero on the new file is a missing-symbol defect, not a clean refactor. When a symbol is defined in a sibling module and re-exported through an intermediate (e.g. `import hermes_cli.auth as auth_mod` then `auth_mod._foo`), verify the chain end-to-end: the definition exists in the leaf module, the re-export import exists in the intermediate, and the consumer imports the intermediate — not the leaf directly.

2. Scan added lines from the complete pinned-base diff established in Step 1, plus explicit new-file contents. Do not scan only `git diff --cached`, because an unstaged implementation can have an empty index while still containing the entire change.
2. Flag credential literals, untrusted shell interpolation or `shell=True`, dynamic `eval`/`exec`, unsafe deserialization and SQL built from untrusted interpolation. Use `search_files` and bounded `read_file` windows to trace the matched inputs and callers before classifying a defect; a token match is a lead, not a verdict.
3. Pass sanitized categories and `path:line` references to the reviewer. Keep suspected secret values out of chat and handoffs, because repeating a literal during the scan can itself disclose it.
4. Require complete bounded records before trusting parsed prefixes. Trace the actual I/O abstraction and stated trust model before alleging truncation: low-level `os.read`/`pread` and blocking buffered `read(size)` do not have identical short-read contracts. Check aggregate cap-plus-one accounting, finite read bounds, verified EOF or conservative completeness refusal, checked closure and permanent HOLD before dispatch. Exercise a valid JSON prefix hiding a corrupt/oversized tail and a later I/O error through the concrete reader and its actual consumer, with positive complete/split/exact-cap controls; never credit one successful low-level chunk as the whole document or invent a defect solely from the number of read calls.

5. Derive expected kernel pseudo-file bytes and key sets from retained producer output and the concrete consumer, not assumed schemas or newline conventions. Compare observed fields with the parser's allowlist, required masks and authoritative budget field before admitting a native case; additive fields can cause an intentional compatibility refusal even when the producer succeeded. Do not bypass that refusal by dropping unknown fields or changing host settings. Any authorized schema extension needs regressions preserving duplicate, malformed, overflow, missing-required and pressure-event refusal plus unchanged budget accounting. Cover exact empty/nonempty snapshots and read errors; keep lexical recognition checks distinct from execution of the native parser.

6. Trace nested cleanup and nonreturning failure helpers across admission boundaries, not only the top-level refusal branch. Descriptor custody is not permission to write: require explicit admission before central journal I/O and cover pre-admission cleanup failures plus an admitted positive control with accurately labelled source/synthetic proof.

7. Before alleging a low-level POSIX failure, trace the concrete runtime wrapper, including iterator cleanup. For example, CPython v3.14.8 duplicates an FD for `os.scandir(fd)` but calls `rewinddir` before `closedir` on exhaustion/context exit, so shared duplicated-FD offsets alone do not establish a successive-scan EOF defect. Inspect the pinned wrapper source and retain its limits: upstream source is not installed-binary or alternate-runtime equivalence. Never run a default-backend reproduction to settle this inside a source/mock-only lane; admit dynamic proof separately.

8. Treat Python `-B` and `PYTHONDONTWRITEBYTECODE` as bytecode-write controls, not source-only execution. A source hash followed by `SourceFileLoader.exec_module` can still select a pre-existing unchecked-hash or timestamp/size-matching cache. For source-identity execution gates, bind the actual executed code to the same bounded verified bytes, with correctly initialized module metadata, or explicitly qualify a separate cache policy. Add both cache forms and a post-admission source-change refusal under the real consumer; do not let an earlier source-identity guard mask the loader boundary.

9. Trace expected artifact identity from its authoritative capture through copying, manifest generation and final consumers. Rehashing a changed extracted member can produce an internally consistent manifest without preserving the identity whose dependencies were inspected; compare tools and libraries under the same claimed invariant. Distinguish historical custody digests from checks actually enforced downstream: storing a digest does not implement consumer revalidation. Correct an overstated claim rather than silently expanding trust policy; use the TDD skill's closure-to-runtime regression procedure when a behavioral fix is required.

## Step 3 — Baseline tests and linting

Before selecting a native check, trace its concrete startup guards and compare them with passive metadata for the actual artifacts, caller and workspace. For hard resource claims, distinguish renewable per-period bandwidth from cumulative lifetime CPU, cgroup charged memory from physical RSS, and kill/freeze requests from observed cessation. Require source-backed enforcement-delay and post-cutoff bounds; counters, hypothetical certificate values or successful stress tests alone do not prove a never-exceed ceiling. Preserve the original guarantee until the user explicitly approves different semantics. Compiler success does not establish runtime ownership, protection or filesystem-capacity prerequisites. Keep source acceptance, conditional provisioning approval and execution admission separate; never invoke a produced artifact or real/default backend merely to diagnose readiness. Use [passive native-entry readiness](references/native-entry-readiness.md) for the comparison procedure and narrowly scoped approval boundary.

Detect the project language and resolve its test interpreter independently of the orchestration kernel's `sys.executable`; probe required framework imports through that exact executable before a large run, because the control plane and project tests may use different environments. Use the canonical runner and actual guards. Preserve its maintained per-file timeout rather than inheriting a shorter cap from an old recorder; a timeout caused by that cap is incomplete proof, not an assertion regression. Preserve the failed run, confirm child cleanup and rerun the missing file under the maintained bounds. Inspect each selected suite's private HOME/HERMES_HOME/XDG and runtime-bin contract before sharing a generic recorder; instantiate the required private directories under evidence rather than weakening the guard, and retain setup refusals separately from behavioral failures. Before materializing a baseline, trace the selected tests' complete read closure: a review's core-source snapshot may omit checkpoint manifests, pinned preimages or fixture data needed by its test runner. Include adjacent service templates read by renderers, not only Python/JS modules. For generated-service regressions, identify whether the first render command or the later replay assertion failed before selecting instrumentation; a generic refusal from a missing template is not proof that input acquisition or replay failed. Restore those inputs only from verified frozen originals; classify missing-fixture errors as materialization failures, not behavioral RED, and rerun under a fresh label without weakening the guard. If the recorder binds only source/test directories, supplement it with a parent catalog of the actual metadata, preimages and fixtures consumed. When a baseline comparison is necessary, run it in a separate pinned checkout with identical isolation. Never stash, reset, restore or switch a dirty primary to manufacture a baseline. Preserve exact exits, terminal summaries, failure identifiers and input bindings; compare new failures with the real baseline.

Reuse the maintained guarded runner even when its receipt root belongs to an earlier evidence directory. If that root remains within authorized write scope, explicitly permit only new create-only labels such as `<slice>-red-<unique>`, `<slice>-green-<unique>` and `<slice>-full-<unique>`, then index their exact paths and hashes from the new handoff. Do not edit the runner's output-root constant merely to relocate evidence: that changes hash-bound test infrastructure without advancing the correction. Preserve all existing leaves, and never use a predecessor directory to bypass a denied write.

When an isolated lane genuinely requires a separately authorized runner adaptation, finish it before capturing the actual lane-start manifest. Supply the original and adapted bytes with their exact generated delta, retaining the accepted historical binding separately; a pre-adaptation hash labelled as current can otherwise create a false integrity failure and strand a valid proof handoff.

1. Select focused tests from the changed consumers and negative paths, then the project's appropriate broader checks. Use commands from maintained manifests/runners rather than enabling no-test success or weakening type/lint flags to obtain green. For refusal tests, satisfy earlier guards and assert the intended exception class plus a stable error code or specific escaped/anchored diagnostic, along with absence of the effect that guard protects. Reject helpers that count any caught exception as success: an unrelated setup error can otherwise pass without reaching the intended refusal. When fixture reachability is uncertain, verify the corresponding valid setup reaches the guarded boundary before crediting its negative cases.
2. Run each check through `terminal` or the existing receipt recorder with a bounded wait. Preserve its actual child exit, exact command/cwd, source/environment bindings and full private log before parsing a summary; piping a test into a display command can replace the test's exit with the display command's exit.
3. For a Python project whose maintained workflow permits direct pytest, use the recorded interpreter with `-B -m pytest -q -p no:cacheprovider <selected-test-paths> --junitxml=<evidence>/junit.xml` through `terminal`. Retain the project's real isolation and fixture-root guards, and compare collected nodes, JUnit identities and terminal counts rather than treating the final log line as complete proof.
4. Run maintained lint/type commands when available and authorized. Record omissions explicitly; if a missing check is required acceptance proof, keep HOLD rather than silently treating its absence as success.

**Reuse by verified dependency, not receipt-wide freshness.** A recorder may hash every test file even when a particular suite does not use them. Enumerate all mismatches, trace actual imports/callers and fixture or generated inputs, and require every relevant production, selected-test, shared-helper, producer and environment binding to match before reusing that suite. Record each excluded unrelated binding and its reason, exercise the changed test separately, and rerun the affected suite whenever dependency relevance is uncertain. Never use a filename-based exemption or rewrite the original receipt to hide drift.

Reconcile the receipt catalog by command, selected testcase identities, relevant environment and source generation before debugging a retained failure or assigning recovery work. Mark an older failure superseded only when a newer valid passing execution covers its failed identities and preserves the intended assertions; filenames, a stale draft and the last receipt alone do not establish that frontier. Preserve the original failure and name its superseding receipt, because an interrupted worker may have fixed and tested it without updating its handoff.

Choose the successor's role from that verified frontier. Resume an unchanged causal RED at its missing GREEN, not broad discovery. Once current source and the required full checks already pass, keep missing self-review/readiness/handoff work read-only with respect to source and put new reports in a separately owned output root; another implementation assignment can disturb already-proved bytes without filling the actual gap. Report any newly found defect for a separately authorized correction. Keep missing independent acceptance open: neither a recovered test pass nor completed closeout paperwork supplies that verdict.

Track freshness per command after each edit. Where a trusted grader binds the source manifest, compare that manifest to the exact current tree before execution and refresh only authorized owned entries after source, test, guard or documentation edits; preserve immutable fixtures, budgets and case identities. A stale-binding refusal is setup failure, not a behavioral RED, and repeating the same unchanged invocation cannot repair it.

Do not promote a pre-fix full matrix to current merely because a post-fix focused suite passes: tests, strict lint, formatting and documentation are separate checks and can diverge. Rerun affected checks or label their older passes historical/pending; report a newer relevant failure instead of an older green aggregate, and explicitly correct any earlier completion overclaim. Report fresh executions and reused proof separately, deduplicating repeated cases rather than adding historical replay counts.

Use [evidence recovery](references/evidence-recovery.md) for schema/type checks, dependency-scoped receipt reuse and interrupted-review handoff.

**Baseline comparison:** If baseline was clean and your changes introduce failures,
that's a regression. If baseline already had failures, only count NEW ones.

## Step 4 — Self-review checklist

Quick scan before dispatching the reviewer:

- [ ] No hardcoded secrets, API keys, or credentials
- [ ] Input validation on user-provided data
- [ ] SQL queries use parameterized statements
- [ ] File operations validate paths (no traversal)
- [ ] External calls have error handling (try/catch)
- [ ] No debug print/console.log left behind
- [ ] No commented-out code
- [ ] New code has tests (if test suite exists)

## Step 5 — Independent acceptance

1. Decide whether independent review is required from the risk and active operator contract, not whether the session is interactive. Ordinary low-risk one-shot work may use the prescribed self-review path; high-risk security, funds, consensus, unsafe code, concurrency or broad-blast-radius changes still require their independent acceptance gate.
2. Resolve the currently authorized independent read-only executor route. Follow the `claude-code` skill for an Opus-Max lane only when available and permitted; an unavailable or prohibited reviewer leaves HOLD, not permission to substitute the implementer. Obtain explicit agreement once before changing a required review route. Once the user selects an alternative, preserve that decision and dispatch it rather than asking again or waiting for the former provider's reset. A route change does not alter preservation, runtime, billing or publication limits.
3. Freeze the assigned source/evidence set and give the reviewer its manifest fingerprint, exact content/mode and patch bindings where applicable, sanitized scan leads, relevant invariants and compact receipt/log pointers. Name separate review-output ownership and the precise non-writing checks, if any, that may run. For hand-written derived models, require inspection of the actual guards, receiver mutations, argument order, return paths and failure preconditions; a reference resolving to an admitted address establishes input coverage, not the truth of the associated semantic claim. Allow scoped inspection of definitions and callers; diff-only review can miss a boundary outside the changed hunk. Do not forward the full implementation transcript or allow a second source writer.
4. Pin the approved provider, model and effort atomically in the same turn as native dispatch; a category name alone can select an excluded executor. Use the supported per-lane route tool when available, not hand-edited configuration. Persist approval, source fingerprint, requested route, delegation handle and output path before yielding. Restore prior routing without retargeting the constructed child. Keep requested configuration, observed runtime initialization and provider-attested served identity separate. Require initialization/model usage before calling a route active; preserve an absent served-identity field as unknown rather than promoting a configured alias to provider attestation. Label Max effort as explicitly pinned or observed for that particular lane, never inferred from the parent, model name or a sibling reviewer. Apply the lane's actual identity-evidence requirements rather than inventing a new gate from missing optional telemetry. Disable unapproved automatic fallback and classify route failures separately from source findings.
5. Require a terminal verdict with explicit coverage. Permit a fail-fast BLOCK once a material defect has a cited source-level causal trace or an executed reproduction; require the actual unreviewed remainder rather than spending the whole budget searching for more defects. Use HOLD for missing proof without an established blocking defect, and PASS only for the complete assigned scope. An inspected-path list alone does not establish completed review. Label static findings as source-derived, require path/line evidence, and retain exact commands/exits only for reproductions actually performed; proposed commands remain unexecuted. Keep nonblocking suggestions separate and retain the complete structured judgment. Before crediting it, read back that exact artifact, establish reviewer completion, and revalidate its source/support bindings. Preserve earlier BLOCK/HOLD records and append a superseding result instead of rewriting history.

Passing fixtures, a repaired finalizer, matching hashes or a successful parent reconstruction establish their stated proof only; none supplies a missing independent verdict.

If only report finalization failed, apply [completed-verdict recovery](references/evidence-recovery.md#6-recover-a-completed-verdict-after-report-finalization-failure) before crediting the retained judgment. The size-preference rule above still applies; missing scope, source identity or required supports cannot be repaired by packaging.

Keep optional tracking failures separate from review/test failures. If a verdict record requires a missing checkpoint ID, preserve the verified review in a parent-bound artifact and update the current plan; never attach it to an unrelated checkpoint or fabricate an accepted scope merely to satisfy metadata validation.

## Step 6 — Evaluate results

1. Reconcile actual check exits, exact baseline failure identifiers and the independent verdict against the original milestone's acceptance criteria, not just the last worker's narrower assignment. Record component acceptance separately from aggregate completion: a bounded-slice PASS with an overall-tier HOLD leaves the parent milestone incomplete, even after a successful copy or freeze. Mark the verified component complete and activate the next missing authorized stage; do not keep a complete source-review item blocked on later native, packaging or integration obligations. If the checklist was closed prematurely, reopen that item and append a correction while preserving accepted source/proof and earlier records; do not rerun valid proof or shrink the milestone to manufacture completion. Report nonblocking suggestions and inherited out-of-scope failures separately from introduced defects.
2. Keep HOLD for missing required proof, an unavailable reviewer or an unfinished review. Preserve the checkpoint and name the next missing obligation; more implementer activity cannot fill an independent acceptance gap. When the user disputes a verdict, trace each blocker back to the accepted contract and current evidence rather than merely repeating the saved conclusion. Correct stale or unsupported gates without erasing real findings or granting new authority.

   Keep admission scoped to the action being proposed. Bind each blocker to the action and its traced call-path dependency: a native-only prerequisite does not automatically block independently admitted source work or a compiler-only path that does not consume it. A tool-free source judgment does not prove native behavior or host health, but pending runtime clearance alone must not block that separately authorized source review. Do not promote a reviewer's proposed prerequisite into user policy. Label it as a proposal unless the admitted contract requires it, because a telemetry limitation alone does not establish a fault or authorize a new mandatory configuration. Retain the unmodified bound report and state any parent interpretation limits explicitly; real required proof gaps remain HOLD.
3. Route sufficiently evidenced in-scope findings to Step 7 only when fixes are authorized. Keep a source-derived causal finding distinct from an executed reproduction, and require the intended failing regression before changing production behavior. A PASS with nonblocking notes remains acceptance of its frozen scope: if follow-up hardening is authorized and useful, seed a separate writable candidate from that accepted checkpoint, preserve the original verdict and require new proof/review for the changed scope. Do not invent a BLOCK to justify improvements or repair a baseline failure or accounting-only discrepancy merely to make every status green.
4. Proceed to Step 8 only when applicable acceptance gates are satisfied and the current task authorizes a commit; verification does not itself grant publication or integration authority.

## Step 7 — Bounded fix-and-reverify loop

1. Assign evidenced findings to the authorized sole implementation writer; keep the independent reviewer read-only, because letting it repair its own findings collapses the acceptance boundary. Confirm the previous owner has stopped before transferring the checkout. Distinguish a worker's parent-decision stop from a user-owned approval gate: when autonomous source correction is already authorized, the parent can choose a bounded fix in a fresh candidate without asking the user to accept residual risk or repeat approval. Preserve the accepted baseline and require new proof/review; this choice grants no native execution, activation or other hard-line authority.
2. Give the executor the frozen base, exact finding references, any actual reproduction commands/exits, current candidate and allowed paths. For a static lead, make the discriminating regression its first obligation rather than claiming the reviewer ran it. For stateful invalidation, pin the contract's discard/retention rules by prewarming valid retained state, adding pending work, and then exercising zero-delta transitions and cumulative expiry across individually admissible gaps. Include idle/no-pending controls, because empty-start or transition-pair-only tests can miss stale-state resurrection. Save the exact failing source and test preimages before either changes again; a hash-only receipt cannot recover lost bytes. If the existing production branch already behaves correctly, label new coverage as characterization instead of manufacturing RED or an unnecessary production edit. Repair only verified in-scope defects; do not broaden into unrelated cleanup or authorize commit/push implicitly.
3. Re-run Steps 1–6 against the complete original-base candidate, not only the latest correction or closure of the last finding. Keep inherited-preservation preimages and digest guards pinned; permit exact reviewed edits instead of refreshing a baseline hash merely to obtain GREEN. Use the [correction-generation recipe](references/evidence-recovery.md#correction-generations-after-a-source-block) for byte-preservation guards and RED snapshots. Permit at most two authorized correction cycles before escalating with preserved changes, real failed receipts and the smallest remaining decision.
4. Preserve unrelated dirty work and the verified checkpoint when blocked. Do not recommend broad stash/reset/restore as an automatic undo; those operations can erase or hide work owned by the user or another lane.

## Step 8 — Commit

If verification passed and the active task explicitly authorizes a local commit, stage only the complete explicit owned-path set and create one descriptive coherent commit. Leave unrelated and pre-existing dirty paths unstaged. The supervisor checks the destination and complete outgoing range before any separately authorized push. Independent acceptance does not itself authorize commit, push, integration, live configuration or deployment.

## Pitfalls

- **Empty staged diff** — inspect the complete assigned staged, unstaged and untracked set before reporting nothing to verify; an unstaged implementation must remain reviewable without changing the index.
- **Not a Git repository** — use the manifest-based review path in Step 1; absent Git metadata does not invalidate a preserved source or evidence packet.
- **Large diff (>15k chars)** — split by file, review each separately
- **Unparseable reviewer handoff** — request one bounded correction only after the reviewer process is confirmed complete; retain HOLD if the terminal verdict remains unusable.
- **False positives** — if reviewer flags something intentional, note it in fix prompt
- **Unavailable test/lint check** — record the omission and its effect on acceptance; keep HOLD when required proof is missing instead of silently skipping it.
- **Auto-fix introduces new issues** — counts as a new failure, cycle continues
