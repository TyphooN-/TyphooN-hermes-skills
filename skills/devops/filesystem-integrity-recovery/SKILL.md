# Filesystem Integrity and Recovery

## Portable scope

This copy preserves a locally developed workflow, not transferable approval. Resolve the current task, repository, active Hermes profile, tools and ownership on this machine first. Historical project choices and TyphooN-specific executor/build policies are context, not permission to start services, run targets, modify security settings or publish. Project-root variables are documented in the collection's `PORTABILITY.md`; unset variables are not usable paths. Installing a skill installs no external tools or plugins.

Use when the user asks to check or repair filesystem corruption, validate files after crashes, interpret scrub/SMART results, or remove allegedly corrupted files. This is storage and content-integrity work, not application core-dump analysis or disk-space cleanup.

## Execution contract

Resolve the latest steering before starting any storage commands. If the user cancels the repair request or assigns it to another session, stop this session's diagnosis, scrub monitoring, and repair work; even read-only polling can duplicate ownership and distract from the task that remains authorized. A later ambiguous continuation does not revive the explicitly cancelled repair. Touch an existing operation only when this session owns it and the cancellation requires a safe handoff.

When TyphooN asks to check/repair and that request remains active, start a meaningful authorized diagnostic after prerequisite discovery instead of ending with another explanation or list of suggested checks. Report actual progress briefly and carry the work through result classification. Safety is a reason to gate destructive repair, not to stop safe diagnosis.

Distinguish commands that display a previous result from commands that launch a new check. Do not imply that a status query started a scrub. A running audit is not a completed audit; keep ownership until exit and report interpretation, or clearly identify an authentication/offline/user-steering blocker.

## Procedure

1. **Read the supplied evidence first.** Use `read_file` for logs and scripts, and `vision_analyze` for screenshots. Inspect a repair script before running it: names do not disclose automatic package reinstalls or destructive operations.
2. **Map current storage and activity.** Use `terminal` for `lsblk -o NAME,TYPE,FSTYPE,SIZE,MOUNTPOINTS` and separate `findmnt --target <mountpoint>` calls. Identify encryption layers, filesystem UUIDs, shared subvolumes, separate boot partitions, and network mounts. Check existing scrub, defrag, balance, package-manager, and repair processes before adding load; do not stop user-owned processes without authorization.
3. **Define coverage.** Separate device health, filesystem checksums/metadata, package files, user-data integrity, and application consistency. Deduplicate checks by filesystem rather than checking every subvolume separately. Avoid repeating an already completed recent full scrub without a reason. For a known, small failure inventory, start with the saved scrub records, current subvolume identities, exact live paths, and existing receipts. Stop discovery once those establish the next authorized action; widen journal history or inode/filesystem scans only to resolve a specific contradiction or unidentified damage, so a narrow cleanup does not become an open-ended forensic investigation.
4. **Run safe evidence collection.** For Btrfs, inspect scrub status, device counters, filesystem usage/profiles, and relevant kernel errors. Read SMART health and, when warranted, detailed error logs. Discover actual devices first; never copy device names from an old session. Use installed help/current primary documentation for unfamiliar options.
5. **Audit file contents against trusted sources.** On Arch, capture complete `LC_ALL=C pacman -Qkk` output and its exact exit status, checking installed-version semantics. Prefer the installed checker once its content-checksum coverage is established; build a replacement auditor or acquire another tool only to close a demonstrated coverage gap, not merely because an alternative checker is absent. Classify missing files, digest/size differences, metadata differences, expected configuration edits, permission denials, and operational failures separately. Use repository/object checks plus separate, attribute-aware working-tree validation for Git; refresh a rebuilt temporary index before interpreting stat-based differences, because a new index has no checkout stat cache and expected EOL conversion is not corruption. Use trusted manifests/backups for downloads and models, and appropriate consistency checks for databases. Before interpreting SQLite `file is not a database` as corruption, establish whether the application uses SQLCipher or another encrypted format: a plain SQLite reader cannot validate an encrypted database without the correct engine and key. Keep package integrity, database readability, and application login persistence as separate claims. Do not read secrets into model context or indiscriminately hash credential stores.
6. **Keep long checks observable.** Use a private unique evidence directory, persistent stdout/stderr, process handle/PID, and saved exit code. For bounded background checks enable completion notification. When reboot/rescue transitions are plausible, preserve authoritative logs in a private persistent directory, not only `/tmp` (which may be tmpfs). Read generated collectors back, verify nonzero size and required commands, and run `bash -n` before handing them to the user; a write-tool success response alone is insufficient. Save potentially large kernel queries to a private evidence file before displaying results; parse timestamp ranges, deduplicated path/inode inventories, counter discontinuities, and bounded representative errors instead of dumping the boot journal into model context. Inspect small progress summaries with backoff rather than ingesting full logs. A wait timeout is not process completion. Wrapper exit 0 does not establish child-check success: inspect the recorded per-command exits. Missing process handles, empty logs, or absent exit markers require artifact and live-process inspection; report interrupted/inconclusive rather than clean. After the user reports running a collector, inspect its output immediately and classify findings instead of merely acknowledging completion or restarting collection.
7. **Stage and execute only justified repairs.** Identify exact files and trusted restoration sources. Preserve backup/configuration/user changes. Package reinstall, deleting damaged files, offline filesystem repair, unmounting boot volumes, and rebooting require their applicable approval and safety boundaries. For confirmed non-backup package-content damage, prefer a signature-verified archive matching the installed package name, version and architecture; reinstall the complete package rather than manually deleting its library, then rerun its audit and independently compare the repaired file with the signed reference. Do not substitute an unrelated upgrade or weaken signature policy to obtain a repair. See the exact-version package-content repair recipe in [Btrfs and Arch evidence patterns](references/btrfs-arch-evidence.md). When the user explicitly authorizes running a modified repair script, carry it through execution and evidence collection rather than stopping at installation; first inspect current scrub/script/package-manager activity and observe an existing run instead of launching a duplicate. For deletion from a previous run, freeze the exact scrub-path inventory from its saved log, excluding package/configuration warnings; reconcile current file identities before mutation and record deleted, already absent, replaced/identity-mismatched, and failed paths separately. A preview manifest is not a deletion receipt: after interruption, inspect actual path state and mutation receipts before reporting completion. When verification still fails, reuse that completed scrub's bounded kernel records for the next authorized cleanup before launching another full scrub; deduplicate by filesystem/subvolume/inode/path and revalidate current identity and read failure. Treat the recovered path set as a lower bound, because error-event totals and available path records need not match. If kernel `callbacks suppressed` messages hide most paths, do not spend repeated full scrubs chasing tiny log inventories: perform a bounded-memory, no-follow read audit of the explicitly authorized disposable artifact scope, record EIO files with stable filesystem/subvolume/inode/size/mtime/ctime identities, preserve readable/changed files, then revalidate before deletion and scrub once. Do not extend that audit/deletion to source, personal data, or other artifact scopes without authorization. Query `btrfs filesystem show` through a mountpoint descriptor, not an arbitrary nested directory descriptor; verify nested directories using subvolume ID and matching `st_dev`. Take the next verification counter baseline after deletion, confirmation reads, and filesystem sync: preview/read checks can themselves increment corruption counters. Recheck affected content after repair.
8. **Gate replacement snapshots on completed cleanup and verification.** When the goal is a repaired baseline, finish live-file cleanup and authorized removal of damaged snapshot references, wait for Btrfs deletion cleanup, then complete a read-only verification scrub with zero uncorrectable errors and no device-error counter increase before creating replacement snapshots. Do not create a fresh snapshot while scrub or cleanup is running: it can pin the same damaged extents that subsequent live-file deletion needs to release. If the user explicitly wants a provisional preservation checkpoint instead, explain that tradeoff before creating it; a warning label alone does not make it a clean baseline. Map each requested snapshot scope separately: a root snapshot does not recursively capture separate `/home` or other nested subvolumes. See [Btrfs and Arch evidence patterns](references/btrfs-arch-evidence.md) for the Snapper reset and replacement recipe.
9. **Finish with a coverage ledger.** List completed checks and exact results, confirmed damage, inconclusive/unreadable paths, repairs actually performed, remaining offline/authentication steps, and evidence paths. Never equate “no matching warning lines” with a successful audit.

## Authentication

Tool approval and sudo authentication are separate gates. If sudo requires local authentication, explain the blocker once and arrange a local terminal command that saves restricted diagnostic output for subsequent reading. On an authorized desktop workflow whose installed policy supports Polkit, use `pkexec` for the bounded operation and let the user authenticate in the desktop prompt instead; do not change privilege policy. Track that process without launching a second prompt. Determine authentication state from the tracked process's current executable/command and fresh operation status, not an empty log or absent child. Inspect `ps -p <pid> -o pid,ppid,comm,args` and, for a scrub, capture a fresh `btrfs scrub status <mountpoint>` through the authorized privilege route. `pkexec` can exec the requested program in the same PID, and a foreground scrub can buffer redirected output until completion; neither no descendant nor no final receipt proves authentication is still pending. Report pending only while current evidence still shows the authentication stage, and distinguish a genuinely running command from completed verification. Never request passwords in chat, embed them in shell commands, or weaken sudo policy. Do not repeatedly retry identical noninteractive sudo calls after the requirement is established. Continue independent unprivileged checks where useful, explicitly marking their permission-related coverage gaps.

## Host-integrity gate during application verification

When crash debugging or build verification reveals checksum failures, compiler crashes, disappearing devices, or repeated reboot interruptions, distinguish the application defect from the host-integrity investigation. Do not infer that one caused the other.

- **Gate on current evidence, not historical counters alone.** Fresh uncorrectable checksum findings in relevant artifacts or unresolved host instability justify pausing artifact publication and large verification loads. A cumulative counter by itself does not establish ongoing corruption or an indefinite blocker. Continue bounded read-only diagnosis and state the exact condition needed to resume.
- **Classify the affected paths.** Extract and deduplicate checksum-associated paths from preserved kernel evidence. Separate generated objects/caches, coredumps, package-managed files, source/configuration, and irreplaceable user data. Report the captured path set as a lower-bound inventory, not a filesystem-wide clearance. Do not clean a build tree while another writer uses it.
- **Refresh resources after a reboot.** Re-enumerate device identities, GPU ordering, usable memory, and active verification/inference processes before reusing a launch command. A topology change should fail the old resource plan closed; reassess or report it, rather than forcing the old device indices or stopping another owner's workload.
- **Validate selected rollout artifacts without claiming host clearance.** A privately staged same-pin runtime may be copy/hash checked and cold-probed on a separate loopback port without loading weights or changing the live service. Include the server implementation shared library, preserve SONAME symlinks, and verify actual `/proc/<pid>/maps` origins as well as exact alias catalog parity and clean child exit. Validate large model contents by bounded-memory streaming SHA256 against primary publisher metadata at the pinned revision. These checks establish selected content/functionality at that observation time, not a clean filesystem or an independent backup.
- **Keep proof levels separate.** Collector exit status, scrub result, source consistency, binary provenance, numerical regression, model warmup, generation, and deployment are distinct claims. A harness assertion after successful warmup is a harness failure, not evidence that the model failed to load. Preserve the failed attempt, narrow the erroneous check, and verify process cleanup before a bounded retry.
- **Rebuild the complete runtime across ABI changes.** A previously verified same-revision mixed CPU-graph/HIP composition does not authorize reusing that HIP backend after an upstream ggml ABI/SONAME change. Build graph, backend, shared server implementation, and required common libraries from the new revision. Stage the full shared-library closure with SONAME symlinks; hash-check copies and verify actual cold-server map origins before activation. A version command alone does not prove dependency isolation.
- **Respect Git clean filters when checking source content.** Hash regular tracked files through `git hash-object` in their checkout so `.gitattributes` normalization applies; raw-byte hashes can misclassify a correct CRLF checkout as corruption. Check symlink target bytes separately, retain exact-base identity and full expected dirty-path coverage, and keep the real index unchanged. Do not rebuild or repair a disposable checkout merely because its bytes differ from normalized Git blobs.
- **Verify declared patches without accepting arbitrary dirty source.** Pin the exact upstream base and SHA256 of each patch; reconstruct the expected tracked tree through a temporary Git index, then compare the actual tracked source tree. Before trusting `git status` or taking a clean/no-patch shortcut, inspect `git ls-files -v -z` and reject uppercase `S` or lowercase status tags: `skip-worktree` and `assume-unchanged` can hide files the compiler still reads. Do not clear user index flags automatically. Test hidden edits to an unrelated tracked file under each flag, both with and without a declared patch manifest, and verify that refusal leaves the real index unchanged. Reject absent required patches, additional tracked edits, changed patch bytes, and escaping paths. Resolve each patch path against the canonical repository's literal patch-directory boundary; resolving a symlinked boundary itself can wrongly admit an outside directory. Apply the untracked-compiler-input guard in `llama-cpp-upstream-refresh` before claiming exact-source verification: ignored source headers are compiler inputs, not exempt generated outputs. Leave the real index and source unchanged, and disclose temporary Git objects and explicitly excluded build outputs as separate integrity surfaces.
- **Bind regression comparisons to the recovered base.** Compare identical test manifests and execution settings against the implementation's exact base, not an advanced primary checkout; compare failing test IDs, because aggregate counts can hide new failures or reflect different coverage. Confirm each test process imports its intended checkout before using its receipt. See the baseline-comparison recipe in [Qualification evidence across reboots](references/qualification-evidence-across-reboots.md).
- **Preserve upstream regression interfaces when forward-porting.** Retain current filters, backend selection, distribution parameters, and callback userdata types/lifetimes. Sweep newly added production call sites, reproduce any uncovered defect before extending the helper, and run focused plus registered regressions. Capture each command's exit or use fail-fast sequencing so a successful final diff check cannot conceal a compile failure and stale-binary test.
- **Preserve independent evidence.** A checkpoint on the affected filesystem is useful but is not an independent backup. Another directory, snapshot, reflink, or copy on the same device does not provide independent storage-failure protection. Use a trusted separate destination for irreplaceable data and preserve dirty source ownership before regenerating disposable artifacts.

See [Host-instability evidence triage](references/host-instability-evidence-triage.md) for interpretation and recovery gates from application-verification incidents.

### Continuing qualification when host trust is unresolved

If the user explicitly redirects to qualification, follow that scope rather than repeatedly substituting storage diagnosis. Determine which bounded tests are safe under current evidence; keep functional observations **provisional** and retain separate integrity, independent-review, and activation gates. Explicit continuation is not permission to disable admission policy or publish untrusted artifacts.

- **Check ownership before dispatch.** A reboot can restart an existing systemd qualifier and its model children. Inspect the current worker and GPU owners before resuming an isolated lane. Observe its receipts instead of launching a competing model load; do not stop user-owned workloads to obtain capacity.
- **Report receipts, not apparent aggregate progress.** A report can restart at the first model after every boot while durable per-model receipts survive. Preserve a timestamped snapshot, distinguish current-run execution from reused evidence, and validate identity/invalidation rules before calling a cached result current. Historical pass totals are not completed current-run totals. State the exact model/variant, required checks, original test time, and untested coverage; one quantization or Coder variant does not qualify a separate release.
- **Separate capability from operational failures.** A model can pass coherence, JSON, and tool-call checks yet fail the overall gate on unloading or RAM recovery. Conversely, HTTP 500 plus an abort is an infrastructure failure, not a model-quality score. Concurrent builds or other processes can change global memory baselines; do not waive thresholds, claim a leak, or downgrade capabilities without attribution evidence.
- **Turn explicit continuation into execution, not another status loop.** When the user says to continue despite documented host issues, perform the next safe bounded verification within that scope rather than repeatedly returning the same warning. Recheck ownership/resources first. Once the existing qualifier has actually finished, an isolated private test may close missing decode/coherence/JSON evidence without changing the live runtime. Distinguish missing permission from incomplete verification: continuation alone does not authorize repair, policy bypass, deployment, or publication, but subsequent explicit deployment authorization removes that permission gap. Carry it forward and execute the bounded rollbackable cutover once applicable verification is satisfied; do not keep requesting the same approval or presenting an operator-imposed prerequisite as immutable. Preserve unresolved host-risk disclosures and never label provisional deployment as filesystem clearance.
- **Interpret a failed service through its completed report.** A qualifier can finish every selected model and exit `1` because some gates failed; `ActiveState=failed` alone does not establish interruption or a crashed runner. Check the final timestamp, outcome counts, per-model rows, exact process exit, and remaining descendants. Preserve the completed aggregate before a targeted rerun. Select the unresolved models/checks from that report, force fresh execution when closing a disputed result, and redirect the rerun's output to a private evidence directory so a small rerun cannot replace the full catalog report. Require fresh unwaived admission with the original RAM/VRAM tolerances; a previous waived run is not strict evidence. Record admission refusal as no tests executed rather than another model failure.
- **Do not manufacture acceptance through retry churn.** Inspect final error flags, `api_error_status`, `terminal_reason` and result text alongside the result subtype; a `success` subtype can coexist with a quota/API error. After interruption, verify process/session death and compare the current source diff with the saved reviewed snapshot before resuming. Inspect actual implementation, proof and commit state before updating the recovery ledger: an allowlist or report that describes completed behavior can be scaffold without that implementation. Preserve partial verified work and reassign only the remaining scope once ownership is released. Repeated reboot-interrupted reviews are still incomplete reviews; preserve the remaining-work ledger and stop redundant rediscovery/relaunches. Lack of an independent verdict remains an acceptance blocker, not permission to substitute implementer claims. A reviewer quota lockout likewise leaves acceptance incomplete: record the reported reset with timezone, avoid paid fallback/overage and premature probes, and continue only safe work permitted without that verdict.
- **Treat checkpoints as fallible evidence.** Use atomic replacement with file and parent-directory fsync for small JSON control records; retain prior valid records where useful. After reboot, check nonempty, parseable content rather than trusting a previous write-success response. Preserve malformed evidence and create a separate recovery record with unknown exit status when appropriate. Durability measures do not make evidence on suspect storage independently trustworthy.

See [Qualification evidence across reboots](references/qualification-evidence-across-reboots.md) for receipt recovery, runtime ABI checks, rendered-template diagnosis, and authorized versioned-runtime cutover/rollback.

## Application launch/update repair on an unstable host

When an installed CLI silently exits or reports an unsupported installation, first separate **launcher content**, **PATH selection**, **runtime readiness**, and **host integrity**. A working alternative version command is not proof that its normal startup or updater is ready.

- Inspect executable size, symlink/wrapper chain, interpreter, package entry-point metadata, and retained generations before reinstalling. An executable zero-byte script can return success without performing any work; exit 0 alone is not proof of command execution.
- A tiny entry-point repair may remain useful while larger rebuilds are gated. Restore only a verified launcher from trusted metadata or a retained matching package, preserve other state, and check that the shebang begins at byte zero. Re-read the actual file after editing: an insertion into an empty file can accidentally introduce a leading newline.
- Treat startup recovery as potentially mutating. For session loss or database-open errors, inspect the installed version's recovery path before relaunching: some clients delete and recreate an unreadable database. Preserve affected application data before a controlled reproduction; do not use logout, reset, or reinstall as diagnostic shortcuts. An unlocked keyring and an existing secure-storage item do not prove the application can retrieve the correct encryption key; inspect service ownership and lock metadata without fetching secrets. Even an apparently read-only `update --check` can first run dependency synchronization or interrupted-update completion through a bootstrap wrapper. Inspect the launcher/guard and prefer a documented passive readiness probe before testing another installation. Do not remove markers or bypass recovery guards to manufacture a successful launch.
- Separate preview, execution, and health results. A dry-run proving the command now responds does not prove the update executed, activation finished, plugins loaded, or host integrity recovered. Preserve exact exits for each verification command rather than only the final command in a shell sequence.
- Report confirmed truncation separately from suspected cause. Reboots plus zero-length files and checksum findings warrant an integrity investigation, but do not prove which component caused truncation or that unrelated application source is damaged. Map current findings to affected paths and retain a concrete resumption condition rather than an indefinite blanket prohibition.

## Safety and interpretation pitfalls

- `btrfs check --repair` is not routine maintenance. Never run it on a mounted filesystem or recommend it simply to clear historical counters. Offline repair needs backups, a demonstrated structural problem, and case-specific expert guidance. Start offline assessment read-only where appropriate.
- Btrfs scrub verifies allocated checksummed extents; it does not validate arbitrary data already corrupted before checksum creation, unchecksummed data, application semantics, or separate filesystems.
- Treat `corruption_errs` as cumulative error events, not remaining damaged files: deleting files does not lower it, and repeated reads of the same damaged extents can increase it without proving new corruption. Before comparing observations, verify filesystem/device identity and counter continuity; a substantial decrease invalidates the old baseline rather than demonstrating recovery. Preserve timestamped observations and establish a fresh baseline without attributing a reset to an actor unless a receipt establishes it; small out-of-order journal values can reflect concurrent reporting. Judge cleanup by a completed verification scrub with zero uncorrectable errors and no new device-error counter increase. Explain `btrfs device stats -z <mountpoint>` only as an optional, authorized reset of all device-error counters after preserving evidence, never as repair.
- Identify snapshot references before proposing snapshot deletion: live-file deletion cannot free damaged extents still retained by snapshots or other references. Delete only explicitly authorized snapshots after checking recovery value; removing the last reference can eliminate future scrub findings but cannot lower historical counters or fix the underlying corruption source.
- Single-device Btrfs can use `Data,single` and `Metadata,DUP`. Inspect actual profiles: duplicate metadata may permit correction, but does not give file-data redundancy or device-failure protection.
- Defragmentation/compression is a rewriting operation, not corruption detection or repair. It may also compete for I/O and affect snapshot sharing.
- SMART PASSED is limited evidence, not proof of flawless storage. Unsafe-shutdown counts do not prove each event caused corruption; an error-log entry may be a command error rather than media failure.
- Never auto-reinstall everything flagged by a filtered package-check pipeline. Preserve command status and complete output; expected edits and unreadable files are not confirmed corruption. Combined stdout/stderr can interleave warnings into package-summary lines: extract `warning:` anywhere in a line, not only at line start. A nonzero package-check exit can reflect metadata/configuration differences; classify the full log before declaring content damage or operational failure.
- For file-type warnings, inspect symlink metadata and targets without reading sensitive contents. Resolver-managed links, icon substitutions, FAT mount permissions, and runtime group ownership can explain differences, but require evidence rather than blanket dismissal.
- Interpret scrub evidence in order: bind filesystem/device and boot/start identity, obtain the terminal scrub report, then classify corrected, uncorrectable, and unverified errors against continuous device-counter observations. `running` plus `no errors found` means no errors so far. A kernel `finished ... status: 0` proves completion, not by itself zero uncorrectable errors; an absent process or inaccessible status file cannot fill that gap. Report completion separately from cleanliness when the detailed report is unavailable.
- Match kernel evidence to the scrub's boot as well as its timestamps. `journalctl -k` restricts results to the current boot, so after a reboot it can misleadingly return no records for an earlier scrub. Use a known boot ID or `_TRANSPORT=kernel` with a bounded time range across retained boots; preserve the collected output and state unavailable journal coverage rather than treating an empty query as no corruption. For a specific boot, validate the observed UUID, retain its original representation, and use explicit `--boot=<canonical journal boot ID> _TRANSPORT=kernel`. Preserve a rejected query's nonzero receipt and retry the corrected syntax once; `Failed to add match` is argument failure, not missing kernel records.
- Wiping free space, deleting snapshots, or deleting arbitrary suspect files is not a general integrity remedy.
- For explicitly authorized scrub-driven automatic deletion, pair fresh kernel `scrub: checksum error` records with same-device/logical `unable to fixup (regular)` records. Bound collection with kernel journal cursors; map the logged root ID to exactly one writable mounted subvolume, never blindly prepend `/` to a subvolume-relative path. Verify filesystem UUID, subvolume and inode through no-follow descriptor traversal, reject ambiguous/raw delimiter paths and nonregulars, and preserve files now readable or changed during validation. Require a dry-run and fixture proof. Linux has no atomic conditional unlink-by-inode: disclose the residual rename race and require concurrent writers to stop. Missing path evidence does not establish cleanup completion.
- When editing a repair script that is already executing, prepare/test a separate candidate and install by atomic inode replacement after checking the original remains unchanged; do not overwrite the running script in place. Preserve an original backup.

## Verification

A check is complete only with observed process exit, preserved output, classified findings, and explicit coverage limitations. A repair is complete only after the authorized modification and its follow-up verification. If instability may still be corrupting data, investigate RAM/kernel/power behavior before declaring the system trustworthy.
